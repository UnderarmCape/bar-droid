# Freeze features, gate builds, fix touch

The best way forward for BAR Droid is to stop treating the touch playtest as a quest to beat BARb Hard and spend the days before the ~2026-11-25 private release on a release-candidate (RC) stabilisation. That means a feature freeze, one committed smoke round on the dev phone that every build must pass, a short list of hardening gaps that can still lose a player a game, and a small batch of cheap touch fixes that both the playtest and shipped mobile strategy games point to. The evidence supports this. **Seventeen agent-played games logged about fifty UX findings and no crash-class bug.** The agent won against Easy and Medium and lost all eight Hard games, and it lost them on its own slow macro, not on the controls ([PLAYTEST.md](file:///C:/Tools/BARANDROID/bar-droid-app/docs/PLAYTEST.md)). So more Hard games buy little: they cost the one shared phone about 16 hours and say little more about the dock. What does threaten a release user is found elsewhere. The app's own process leaves no stack trace when it crashes. A build menu copy that errors stays gone for a whole lobby session, online too. A fresh install has never been run end to end. The Mesa/KGSL GPU fault freezes 4–12 % of early game starts on the dev phone ([DELIVERY.md](file:///C:/Tools/BARANDROID/bar-droid-app/docs/DELIVERY.md)). The touch findings mostly come from two roots: implicit modes, and the missing hover a mouse gives. Long-press names on the dock's tiles, a singleplayer pause, and taps that land where the finger meant would remove the most frequent snags without touching anything online. This session coordinates the phone, the build trains, the in-play checks and Kailil's Fold7 checklist. The fixer resumes on a ranked list, with one finding and one new test case per commit, and an optional third session takes the Java-side hardening. Every decision that is Kailil's is listed with a default, so nothing waits on him.

## Seventeen touch games found fifty UX snags and no crash

The playtest gave honest value, but the wrong kind for the next three days. An agent played six New Beginning games and eleven 1v1 skirmishes upright on the S23 Ultra, from 21:45 on 2026-11-21 to about 14:20 the next day. From game 3 on, a laptop driver turned its decisions into real touches through a virtual touchscreen. A dev-only widget exported the game as text and paused it on events, and **10,283 touches** were logged. The touches were 7,461 taps, 2,624 drags and 123 holds, and every order went through the app's own controls ([PLAYTEST.md](file:///C:/Tools/BARANDROID/bar-droid-app/docs/PLAYTEST.md)). Easy fell on the second try and Medium on the first. Hard went 0 for 8 because BARb Hard sends cheap, fast raiders from minute two at every outpost at once, and the agent's reaction loop handles one place at a time. The log's own verdict is that "the touch controls did each thing asked; the gap is the agent's own macro" ([PLAYTEST.md](file:///C:/Tools/BARANDROID/bar-droid-app/docs/PLAYTEST.md)). What the games did surface is a cluster of discoverability and mode problems. A parallel fixer session turned fourteen of those findings into five commits in one day, and six of the fixes were confirmed in later games ([fixes.md](file:///C:/Tools/BARANDROID/toolchain/tmp/play/fixes.md)).

The playtest also showed the main weakness of agent findings: the symptom is real but the diagnosis is often wrong. The agent reported the D-gun AIM stick as "a rate, not a direction". The fixer measured the HEAD build first and found instead that the stick only aimed past half its ring. It confirmed the INSERT-on-builders bug as a FAIL on HEAD before fixing it ([fixes.md](file:///C:/Tools/BARANDROID/toolchain/tmp/play/fixes.md)). This matches the published record. TITAN, the best-documented LLM game tester, found 82 % of seeded bugs but raised **about 30 % false alarms** that needed human triage ([arXiv 2509.22170](https://arxiv.org/html/2509.22170)). Screenshot-driven agents in real-time games complete under 2 % of VideoGameBench even when the game pauses for them, because of latency and misperception ([arXiv 2505.18134](https://arxiv.org/pdf/2505.18134)). Developers surveyed on test automation still see humans as necessary to judge feel and to spot inconsistencies ([Politowski et al. 2022](https://ar5iv.labs.arxiv.org/html/2202.12777)). Several playtest findings also carry the driver's fingerprints, such as stale-button taps, chat Enter and 80 ms lobby taps, so each one needs a scripted repro before anyone fixes it.

Other methods find other bugs. Riot made the League of Legends server deterministic, which took most of a year, to get tests driven by recorded inputs, and that caught divergences that happened in only about 1 in 5,000 real games ([Riot](https://technology.riotgames.com/node/84)). Factorio's whole-game tests catch desyncs just by running ([FFF #60](https://factorio.com/blog/post/fff-60)). BAR Droid already has the Recoil equivalent: `tools/engine-gate.ps1` passed the 2026.09.03 phone engine on three server replays with zero desync warnings, and the exact sim rewrite stays switched off online until it has more ([DELIVERY.md](file:///C:/Tools/BARANDROID/bar-droid-app/docs/DELIVERY.md); [ENGINE-DEFAULT.md](file:///C:/Tools/BARANDROID/bar-droid-app/docs/ENGINE-DEFAULT.md)). Random input is cheap, but it stays shallow. In an industrial WeChat study, Monkey covered 19.5 % of code lines ([FSE16](https://mir.cs.illinois.edu/winglam/publications/2016/fse16industry-wechat.pdf)). Flakiness is the hidden cost of on-device suites. Google measured 1.5 % of test runs as flaky ([Google Testing Blog](https://testing.googleblog.com/2016/05/flaky-tests-at-google-and-how-we.html)). Here the GPU driver fault alone ended **5 of 41 engine starts (12 %)** on 2026-11-20, and pad-test once blamed the virtual pad for one ([DELIVERY.md](file:///C:/Tools/BARANDROID/bar-droid-app/docs/DELIVERY.md)). So unless failures are classified, sessions will chase noise.

## Crashes, lost controls and broken online play are the only blockers

The triage rule is simple. Severity and priority are separate axes ([Packt, Modern Game Testing](https://subscription.packtpub.com/book/game-development/9781803244402/10/ch10lvl1sec49/severity-versus-priority)), and only a bug that "makes the game unplayable for any player who encounters it" with no workaround should halt a release ([Bugnet](https://bugnet.io/blog/bug-severity-classification-for-game-developers)). In BAR Droid terms, the blockers are five:

- a crash or hang on launch, in the lobby, at a match start or in a normal game;
- anything that breaks online play;
- loss of a core control (select, move, attack, build, camera) by touch or pad;
- a state the player cannot get out of;
- loss of settings, saves or replays.

Everything else is scored by severity × frequency × reach (both phones or one, every mode or one). It gets fixed only if the fix is small and lands with a test. In the last days, a risky fix to a non-blocker is worse than the bug.

### The app already records most deaths; four gaps remain

The telemetry most advice recommends for a sideloaded game is largely built:

- **Exit reasons.** At every start `GameService` reads Android's ApplicationExitInfo and logs how the last run ended. It shows a plain-words note after a low-memory kill ([GameService.java](file:///C:/Tools/BARANDROID/bar-droid-app/app/src/main/java/com/underarmcape/bardroid/GameService.java)).
- **Health log.** `PerfLog` writes thermal status, thermal headroom, clocks and the GPU driver's memory once a minute ([PerfLog.java](file:///C:/Tools/BARANDROID/bar-droid-app/app/src/main/java/com/underarmcape/bardroid/PerfLog.java)), well within the ADPF guidance to poll no more than once every 10 s ([Android ADPF](https://developer.android.com/games/optimize/adpf/thermal)).
- **Recovery.** `DriverWatch` closes a game frozen by the GPU driver and says why; `Updater` rolls back a set that fails fast.
- **Log sharing.** Share logs redacts battle passwords ([DELIVERY.md](file:///C:/Tools/BARANDROID/bar-droid-app/docs/DELIVERY.md)).

That leaves four gaps, each small and each a release risk.

**First, the app's own process dies without a trace.** The next start logs that the last run ended in "a crash", but no default uncaught-exception handler writes the stack to launcher.log (overhaul item 53) ([DELIVERY.md](file:///C:/Tools/BARANDROID/bar-droid-app/docs/DELIVERY.md)). For a private group of testers who send in Share logs, a crash report without a stack trace is nearly useless.

**Second, nobody knows what an engine crash looks like from Android's side.** Android's native-crash tombstones come through ApplicationExitInfo from API 31 ([ApplicationExitInfo](https://developer.android.com/reference/android/app/ApplicationExitInfo)). They are produced by bionic's crash handler, though, and the engine runs as glibc code under proot, so a tombstone is unlikely. Recoil's own backtrace in infolog.txt is probably the only record. One deliberate SIGSEGV of the engine on the dev phone settles the question and shows what a tester's Share logs would carry. The same probe can test `setProcessStateSummary`: a few bytes of "where am I" (screen, map, game frame) that Android hands back after any death, a low-memory kill included ([ApplicationExitInfo](https://developer.android.com/reference/android/app/ApplicationExitInfo)).

**Third, the build menu can vanish for a whole session.** Within a lobby session nothing falls back to BAR's own build menu. A copy that errors is removed from every game of the session while BAR's own stays off, and a phone patch that applies but errors is never noticed. These are overhaul items 36 and 37, rated MEDIUM-HIGH and MEDIUM ([DELIVERY.md](file:///C:/Tools/BARANDROID/bar-droid-app/docs/DELIVERY.md)). That is a lost core control, online included. BAR ships test releases often enough that the copy has already stood at 199 of Lua's 200 locals (item 34). So the fix needs a companion: a daily `remake-check.ps1` against BAR's newest release, which catches the next break before a tester does.

**Fourth, the first run has never been tested end to end.** The first-run audit found three HIGH bugs (items 14, 15 and 39). Each was fixed and tested with a targeted state setup, but none of the fixes has been tried on empty storage through the ~4–5 GB download, though every recipient of the release starts exactly there ([DELIVERY.md](file:///C:/Tools/BARANDROID/bar-droid-app/docs/DELIVERY.md)).

### Two risks get managed, not fixed, before the release

The GPU driver fault and memory are known and mitigated, but neither can be cured in days. The fault shows up as Mesa's "flush_submit_list: submit failed -1 (Resource deadlock avoided)" followed by a frozen picture. It came in early in a game (4–112 s), on a cool phone as often as a hot one. It did not follow first draws of unit types or camera jumps. Its rate went from about 1 in 25 starts to 12 % on one day ([DELIVERY.md](file:///C:/Tools/BARANDROID/bar-droid-app/docs/DELIVERY.md)). Mesa's own guide first separates faults, recoverable hangs and unrecoverable hangs ([Mesa docs](https://docs.mesa3d.org/graphics-debugging/debugging-misrenderings-crashes.html)), and Mesa's CI deals with hangs by detecting them and restarting the run ([Mesa CI commit](https://lists.freedesktop.org/archives/mesa-commit/2021-December/126819.html)). DriverWatch already does the detect-and-close half. For the release, the round runner should count these faults and rerun once. Fold7 logs read after Kailil's sessions should settle the unknown that matters most: no recorded case exists on his Adreno 830 ([internal audit](file:///C:/Tools/BARANDROID/bar-droid-app/research_notes/BAR%20Droid%20hardening%20and%20UX%20plan/internal_hardening_backlog.md)). Memory is the likelier hit for a real player. Kailil's only logged online 8v8 on the 12 GB Fold7 ran at 30 fps for 11 minutes. It then fell to 10–25 fps under thermal status 3, with the GPU at 160 MHz, and ended in a LOW_MEMORY kill as he left ([DELIVERY.md](file:///C:/Tools/BARANDROID/bar-droid-app/docs/DELIVERY.md)). Android's lmkd kills the foreground app last, on pressure stalls ([AOSP lmkd](https://source.android.com/docs/core/perf/lmkd)), so this is real pressure, not a misread. For the release it belongs in the known-issues list. The cure (a lighter memory set for big online games) is already listed as Kailil's call.

One outside risk deserves a daily look. The app follows the engine version in BAR's launcher config and has a phone build only for 2026.09.03 ([CLAUDE.md](file:///C:/Tools/BARANDROID/bar-droid-app/CLAUDE.md)). RecoilEngine 2026.11.04 was published on 2026-11-19 ([RecoilEngine releases](https://github.com/beyond-all-reason/RecoilEngine/releases)). If BAR's servers move to it during release week, every phone falls back to the official engine. With it come the README's known limits: a 5–10 s stall when the phone turns, and BAR's Settings wider than the screen upright ([README.md](file:///C:/Tools/BARANDROID/bar-droid-app/README.md)). The sea-twin fix would also be gone, since only the phone engine applies its patch ([fixes.md](file:///C:/Tools/BARANDROID/toolchain/tmp/play/fixes.md)). Nobody can say whether BAR moves this week, so the coordinator checks the config each morning, and a move goes straight into the release notes rather than into a rushed engine gate.

## Hidden modes and missing hover explain most open touch findings

Shipped touch ports of PC strategy games solve the same problems the playtest hit, and they converge on a few rules.

**The start of a gesture, not a mode switch, decides what it does.** In ROME II's touch mode a drag pans on terrain, rotates over the sky and draws an order path when it starts on the selection ([Total War encyclopedia](https://r2encv2.totalwar.com/en/manual/single-player/0005_enc_page_help_keyboard_shortcuts)). Construct's RTS decides tap or drag only when the finger lifts, with a 30 px threshold ([Construct devlog](https://www.construct.net/en/blogs/ashleys-blog-2/rts-devlog-input-gestures-1602)).

**Hold-to-inspect replaces hover.** Feral reserves tap-and-hold for tooltips and info panels ([Feral, Building ROME](https://www.feralinteractive.com/en/news/building-rome-the-touch-controls-of-rome-total-war-on-ipad/)), and Company of Heroes shows an ability's description on a hold ([Feral CoH FAQ](https://feralinteractive.com/en/faqs/companyofheroes/1.0.2/ios)).

**Modes stay visible.** A mode slip comes from poor status visibility; the cure is two indicators for the active mode and few confirmation dialogs ([NN/g](https://www.nngroup.com/articles/modes/)).

**Targets are big, spaced and still.** Touch targets of 48 dp with 8 dp between them ([Google Accessibility](https://support.google.com/accessibility/android/answer/7101858?authuser=0)). Elements that need accuracy should not move, and players get a way to change game speed ([Game Accessibility Guidelines](https://gameaccessibilityguidelines.com/full-list/)).

**Bulk tools beat precise boxes.** Even a well-reviewed port turned "gathering 25 soldiers" into a chore ([Gamezebo](https://www.gamezebo.com/2020/02/19/company-of-heroes-ipad-review-a-solid-port-that-plays-great-on-ipad/)). Select-by-type buttons and unit cards that reach off-screen units carry the load instead ([Feral EMPIRE](https://feralinteractive.com/en/games/empiremobile/android-ios/building-an-empire); [Pocket Gamer](https://www.pocketgamer.com/war-legends/hands-on/)).

The dock already follows several of these: the bright green PLACE, the "+ QUEUE" mark, the D-gun's aim line, the factory panel's counts, and type buttons like ALL UNITS and COMMANDER. Its open findings cluster where it breaks them.

The biggest single gap is that a phone has no hover, and the dock has not replaced it. The dock never names a unit or building. A long press on a tile does nothing, so the Advanced Bot Lab's 18 pictures could be told apart only by reading BAR's unit files ([PLAYTEST.md](file:///C:/Tools/BARANDROID/bar-droid-app/docs/PLAYTEST.md)). Kailil's standing rule for the dock is big buttons with no hint text beside them. Hold-to-inspect fits that rule exactly: the name and BAR's one-line role appear only while a finger holds a tile. The second root is implicit modes:

- QUEUE as a sticky Shift that also turns taps on units into add-selects;
- a picked building or armed order that turns a one-finger drag into a nudge or a formation line;
- the D-gun mode;
- the pre-game dock, where a map tap moves the start position;
- the Mission window doubling as the pause.

The fixer's "+ QUEUE" mark was the first step toward two indicators per mode. The third root is touch targets that move or overlap at the dock's top edge. Four of six converter taps went to the camera knob. A tap meant for QUEUE opened the energy panel, because the energy bar stands in QUEUE's place while nothing is selected. Order buttons redrawn a moment after a selection change took taps meant for the old ones ([PLAYTEST.md](file:///C:/Tools/BARANDROID/bar-droid-app/docs/PLAYTEST.md)). The fixer already used the remedy, a short guard after the layout changes, for the pre-game faction buttons in 3104771e ([fixes.md](file:///C:/Tools/BARANDROID/toolchain/tmp/play/fixes.md)).

Haptics belong to the same later batch. Android's guidance is short, crisp clicks tied to how much an event matters, and nothing rather than a buzz ([Android haptics](https://developer.android.com/develop/ui/views/haptics/haptics-principles)), so the batch would add a light tick for an accepted order and a distinct one for a refused placement. Haptics are not a release item. Everything in the table's release rows is LuaUI or RtsTouch input handling. None of it reaches the simulation, so all of it is online-safe by construction. The PAUSE button stays out of online games by design.

## One phone, three sessions and a build train

The binding constraint is one 8 GB dev phone shared through `devphone-lock.ps1`, with holds under about 45 minutes ([devphone-lock.ps1](file:///C:/Tools/BARANDROID/bar-droid-engine/tools/engine-sim/devphone-lock.ps1)). Running every phone script once takes about an hour, before the reruns that driver faults and low-memory kills force ([internal audit](file:///C:/Tools/BARANDROID/bar-droid-app/research_notes/BAR%20Droid%20hardening%20and%20UX%20plan/internal_hardening_backlog.md)). No committed runner exists for the "rounds" the sessions keep rerunning by hand. Owner time is scarcer than phone time: in the last eight days Claude sessions logged about **181 hours against Kailil's 9** ([WORKLOG.md](file:///C:/Tools/BARANDROID/bar-droid-app/docs/WORKLOG.md)). Two practices suit that budget. Anthropic's 16-agent compiler project shared one machine-readable test oracle and enforced it strictly once late commits began breaking existing features ([Anthropic Engineering](https://www.anthropic.com/engineering/building-c-compiler)). And a second session makes the cheapest independent reviewer, asked for evidence rather than "all tests pass" ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)). So the release window runs on a build train. Fixes land on `main` with their own targeted check. Every three to four hours, or once the fixer has three tested commits, the coordinator takes the phone as `train`, installs HEAD, runs the smoke set and frees the phone. The results go to one file, one line per test.

The phone budget fits in a day with slack. Three trains a day at about 35 minutes each take under two hours. Two in-play tours of up to 40 minutes take 80 minutes, and six fixer slots of 20 minutes take two hours. That leaves most of the night for the soak, in chunks of 45 minutes or less, with roughly 15 % spare for driver-fault reruns at the 12 % rate. The smoke set is the suites that guard the release blockers: dock-phone-test, touchfix-phone-test, lobby-phone-test, pad-test, pad-test -Online, overgame-phone-test, camctl-phone-test, touch-phone-test, bridge-phone-test and remake-check, about 25–30 minutes by their stated run times ([CLAUDE.md](file:///C:/Tools/BARANDROID/bar-droid-app/CLAUDE.md)). Everything else runs in the nightly full set. Each hold uses its own lock name, because two background rounds under one name once swapped APKs mid-test.

| Session | Owns | Dev phone | Fold7 | Stops doing |
|---|---|---|---|---|

| Optional new session, `hardening` (Java side, in its own worktree) | Item 53's handler, the engine-crash probe and the state summary, items 36/37's fallback, the daily remake-check script | Short slots as `hardening` | None | Touching the Lua dock files the fixer owns |

Splitting by files keeps the merge cost low. The fixer stays in `bardroid_portrait.lua`, `bardroid_camctl.lua` and `RtsTouch`; the hardening session works in `GameService`, the launcher and `launch-bar.sh`. One significant change landing at a time is what keeps review tractable ([Simon Willison](https://simonwillison.net/2025/Oct/5/parallel-coding-agents/)). Give the new session its own worktree so its uncommitted edits never end up in a train APK ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)). Parallel agents feel faster than they are: METR's trial measured experienced developers 19 % slower with AI tools while they believed they were 20 % faster ([METR](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/)). So the coordinator tracks blockers closed and regressions introduced per day, and adds the third session only while regressions stay near zero.

## Conclusion

The playtest changed what the question is. The touch dock does not lack features. Its trouble is that the same gesture means different things in modes the player cannot see, while a phone has no hover to explain anything. That is why a handful of small, online-safe changes (hold-to-name, a visible pause, taps that pass through to the map, a guard after layout changes) outrank any new control. A Hard win was never a UX milestone, so the agent harness's lasting product is not a win against Hard. It is a regression benchmark that measures touches, retries and misfires per intent on every build, provided it is committed to the repository before `toolchain\tmp` is cleared. The release's largest risks sit outside the dock: the app's own crash leaving no stack trace, a build menu lost for a whole lobby session, a first run nobody has run, the driver fault's unknown rate on the Fold7, and an upstream engine bump the app cannot control. Each of these is cheap to watch and expensive to discover through a tester's report.

The private group is the real playtest. Its value depends on what its Share logs can say, which is why the crash-stack and state-summary work ranks above any polish. Every report that comes back should be answered with the question "which test should have caught this?", and with a new scripted case or replay for each blocker that got through. After the release, the agent tours, the soak and Kailil's Fold7 passes become one loop, and the work the RC list deferred re-enters it on that evidence: grid paging, a larger minimap upright, start-of-drag rules and picking priority.
